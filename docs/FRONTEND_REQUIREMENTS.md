# 945 前端需求文档

版本：v0.1  
日期：2026-07-11  
状态：与 `PRD.md` 对齐后的前端需求稿  

## 1. 文档定位

本文档是 945 的前端需求文档，用于指导后续原型设计、前端实现和前后端接口对齐。

文档优先级：

1. `PRD.md` 是主需求文档和单一事实来源。
2. 本文档只细化前端页面、交互、组件和状态。
3. 如果本文档与 `PRD.md` 冲突，以 `PRD.md` 为准。

本文档已对齐以下决策：

- 产品名称统一为 `945`。
- 第一版使用本地 demo 用户，不做登录注册。
- Agent Chat 的最终位置暂不固定。
- 界面必须预留多语言能力。
- 饮食记录第一版只做手动输入和计划餐确认。
- 暂不锁定视觉风格，后续由 Stitch 原型决定。

## 2. 前端目标

945 前端要做成一个长期使用的健身工作台，而不是一个只有聊天框的 AI Demo。

用户每天打开产品时，应该能快速回答：

1. 今天我要练什么？
2. 今天我要怎么吃？
3. 今天需要记录什么？
4. 最近身体和执行情况怎么样？
5. Agent 建议我接下来怎么调整？

前端的核心任务是把训练计划、饮食计划、身体数据、执行记录和 Agent 建议组织成清晰、可操作、可持续使用的界面。

## 3. 产品形态

第一版采用 **Dashboard + Agent Chat** 的混合形态。

- Dashboard 负责结构化信息展示和高频操作。
- Agent Chat 负责解释、追问、建议、调整和自然语言录入。
- 用户不应该被迫通过聊天完成所有事情。
- 计划、记录和趋势必须以结构化卡片、表单和图表展示。

Agent Chat 的具体位置暂不定，可以先实现为可移动模块：

- 独立页面
- 右侧面板
- 抽屉
- 浮层

后续根据 Stitch 原型和实际体验再决定最终布局。

## 4. 用户入口

### 4.1 新用户

新用户进入引导流程，完成基础资料和目标设置。

需要收集：

- 昵称或用户名
- 年龄
- 性别，可选
- 身高
- 体重
- 训练目标：减脂、增肌、塑形、力量提升、心肺和体能、健康维持
- 训练经验：新手、初级、中级、高级
- 每周可训练天数
- 每次训练可用时间
- 可用器械：徒手、哑铃、杠铃、健身房器械、跑步机等
- 饮食偏好
- 过敏或忌口
- 当前限制：伤痛、时间不足、饮食不规律等

完成资料后进入计划生成页。

### 4.2 老用户 / Demo 用户

第一版使用本地 demo 用户。

老用户或 demo 用户直接进入今日 Dashboard。

首屏优先展示：

- 今日训练
- 今日饮食
- 今日打卡
- 最新建议
- 当前目标进度

## 5. 信息架构

第一版主导航：

1. 今日
2. 训练
3. 饮食
4. 身体数据
5. 建议
6. Agent
7. 设置

桌面端可以使用左侧导航。移动端可以使用底部导航。

## 6. 页面需求

### 6.1 今日 Dashboard

今日页是产品主页面，也是用户每天最常打开的页面。

页面目标：

- 用户在 10 秒内知道今天要做什么。
- 用户在 1 分钟内完成主要打卡。
- 用户看到 Agent 对今天的关键建议。

核心模块：

- 今日状态摘要
- 今日训练卡片
- 今日饮食卡片
- 身体数据快捷记录
- 每日打卡卡片
- Agent 今日建议
- 本周目标进度

今日状态摘要显示：

- 当前目标
- 本周训练完成数
- 今日热量目标和已记录热量
- 今日蛋白质目标和已记录蛋白质
- 最近体重趋势
- 恢复状态：良好、一般、偏疲劳

今日训练卡片显示：

- 训练名称
- 训练类型
- 预计时长
- 动作列表
- 每个动作的组数、次数、重量或强度
- 完成按钮
- 部分完成入口
- 跳过训练入口
- 备注入口

今日饮食卡片显示：

- 今日总热量目标
- 蛋白质、碳水、脂肪目标
- 餐次列表
- 每餐建议食物
- 确认计划餐完成
- 手动记录入口

每日打卡卡片显示：

- 今日体重
- 睡眠
- 疲劳
- 酸痛
- 心情或压力
- 备注

Agent 今日建议要求：

- 内容短，不做长文章。
- 包含一条主建议。
- 包含 2 到 3 条具体行动。
- 可以提供一个操作入口，例如“调整今日训练”或“查看原因”。

### 6.2 训练页

训练页负责展示计划和记录。

需要包含：

- 本周训练计划
- 每天训练安排
- 动作详情
- 训练历史
- 单次训练记录
- 完成率
- 训练量趋势

动作详情包含：

- 动作名称
- 目标肌群
- 组数
- 次数
- 重量或强度
- 休息时间
- 动作提示
- 替换动作入口，P2

第一版不要求动作视频，但可以为后续动作视频或图示预留位置。

### 6.3 饮食页

饮食页负责展示饮食计划和饮食记录。

需要包含：

- 今日饮食计划
- 一周饮食计划
- 每餐建议
- 营养目标
- 实际摄入
- 饮食记录历史

营养展示包含：

- 总热量
- 蛋白质
- 碳水
- 脂肪
- 达成比例

第一版饮食记录方式：

1. 计划餐确认：用户直接确认某餐按计划完成。
2. 手动输入：用户输入食物、份量和估算营养。

第一版不做：

- 食物图片识别
- 条形码扫描
- 外卖平台接入
- 自动识别餐盘

### 6.4 身体数据页

身体数据页负责展示长期变化。

需要包含：

- 体重趋势
- BMI
- 体脂率，可选
- 围度记录，可选
- 最近 7 天、30 天、90 天趋势
- 和当前目标相关的进度解释

不同目标下重点不同：

- 减脂：体重趋势、腰围、热量执行率
- 增肌：体重趋势、训练量、蛋白质摄入
- 塑形：围度、体重、训练完成率
- 力量：训练表现和动作重量趋势
- 体能：训练频率和心肺类训练完成情况
- 健康维持：运动频率、饮食稳定性、体重稳定性

### 6.5 建议页

建议页展示 Agent 生成的历史建议、周总结和计划调整理由。

需要包含：

- 今日建议
- 本周总结
- 计划调整记录
- 建议来源说明
- 用户反馈入口

每条建议需要说明：

- 建议内容
- 触发原因
- 关联数据
- 推荐行动
- 是否采纳
- 风险级别

示例：

> 最近 7 天训练完成率只有 43%，建议先把本周训练从 5 天调整为 3 天，保持动作质量和执行稳定性。

### 6.6 Agent Chat

Agent Chat 可以是独立页面，也可以作为面板或抽屉。

需要支持：

- 解释训练计划
- 解释饮食计划
- 根据用户输入生成记录草稿
- 回答“今天怎么练”
- 回答“这顿饭能不能吃”
- 请求调整计划
- 询问建议原因

Chat 不能替代所有表单。涉及关键数据写入时，需要确认。

示例：

用户输入：

> 今天深蹲做了 4 组，每组 8 次，80kg，感觉很累。

Agent 应该识别为训练记录草稿，并让用户确认：

> 我会记录：深蹲 4 组 x 8 次 x 80kg，主观强度偏高。是否保存到今天的训练记录？

### 6.7 设置页

设置页包含：

- Demo 用户资料
- 当前目标
- 训练偏好
- 饮食偏好
- 单位设置
- 语言设置
- 安全声明
- 数据导出入口，后续功能

第一版不做完整账号系统，但保留未来登录入口位置。

## 7. 关键用户流程

### 7.1 首次生成计划

1. 用户填写基础资料。
2. 用户选择目标。
3. 用户设置训练和饮食限制。
4. 用户点击生成计划。
5. 系统显示生成中状态。
6. 生成完成后展示一周训练计划和饮食计划。
7. 用户可以接受计划、局部调整或让 Agent 解释。
8. 接受后进入今日 Dashboard。

### 7.2 每日打卡

1. 用户打开今日 Dashboard。
2. 用户输入体重、睡眠、疲劳、酸痛。
3. 用户标记训练和饮食执行情况。
4. 系统更新今日状态。
5. Agent 生成今日建议或提醒。

### 7.3 训练记录

1. 用户打开今日训练卡片。
2. 用户查看动作列表。
3. 用户逐项记录完成情况。
4. 用户保存训练记录。
5. 系统更新训练完成率和训练历史。
6. Agent 根据表现给出一句简短反馈。

### 7.4 饮食记录

1. 用户打开今日饮食卡片。
2. 用户选择确认计划餐，或手动记录实际食物。
3. 系统更新热量和宏量营养进度。
4. 如果明显偏离计划，Agent 给出温和提醒。

### 7.5 每周调整

1. 用户进入建议页或周总结。
2. 系统展示本周执行情况。
3. Agent 给出调整建议。
4. 用户确认是否采纳。
5. 系统生成下周计划。

## 9. 多语言要求

第一版必须预留多语言架构。

要求：

- 所有用户可见文案走 i18n。
- 至少预留 `zh-CN` 和 `en-US`。
- 中文作为 MVP 主语言。
- 英文文案可以先保证结构完整，后续补齐质量。
- 用户设置中需要有语言切换入口。
- 日期、数字、单位展示需要考虑国际化。
- 后端枚举值不能直接展示给用户，需要前端映射成本地化文案。

## 10. 响应式要求

桌面端：

- 左侧导航
- 中间主内容区
- Agent Chat 或建议面板可以作为可选侧栏

移动端：

- 底部导航
- Dashboard 单列布局
- Agent Chat 作为独立页面、抽屉或浮层
- 高频记录按钮放在易触达位置

移动端优先保证：

- 今日训练能快速查看
- 今日饮食能快速记录
- 体重和打卡能快速输入

## 11. 状态和反馈

所有核心操作都需要明确反馈：

- 保存成功
- 保存失败
- 正在生成计划
- Agent 正在分析
- 数据不足，无法生成建议
- 高风险健康提示

空状态不能只显示空白，需要引导下一步。

示例：

- 还没有训练记录：开始今天的训练或生成训练计划。
- 还没有饮食记录：确认计划餐或手动记录一餐。
- 数据不足：连续记录 3 天后，Agent 可以给出更稳定的趋势建议。

## 12. 安全和边界

前端需要在合适位置展示边界，但不能打扰正常使用。

需要出现：

- 初次使用时的健康免责声明。
- 高风险输入时的安全提示。
- Agent 建议旁边的“非医疗建议”说明。
- 用户报告疼痛、眩晕、胸闷等症状时，优先显示停止训练和咨询专业人士的提示。

## 13. 第一版不做

前端第一版不做：

- 原生移动 App
- 食物图片识别 UI
- 穿戴设备连接 UI
- 社区动态
- 排行榜
- 复杂成就系统
- 付费订阅页面
- 教练后台
- 多用户家庭管理

## 14. 视觉设计边界

本项目后续会使用 Stitch 做原型图设计，所以本文档不锁定具体视觉风格。

本文档不强制定义：

- 最终颜色
- 字体
- 图标风格
- 动效
- 组件圆角
- 品牌视觉系统

前端实现阶段应优先保证：

- 功能模块完整
- 页面结构清晰
- 交互流程明确
- 多语言能力预留
- Agent Chat 位置可变
- 数据展示不依赖具体视觉风格

## 15. 验收标准

前端 MVP 完成时，应该满足：

- 新用户可以完成资料填写并生成计划。
- Demo 用户可以直接进入系统。
- 用户打开首页可以看到今日训练、饮食、打卡和建议。
- 用户可以记录体重、训练和饮食。
- 用户可以看到基础趋势图。
- 用户可以和 Agent 对话，并在关键写入前确认。
- 用户可以查看每周建议和计划调整理由。
- 移动端可以完成核心每日流程。
- 页面中没有明显文本溢出、重叠或不可点击区域。
- 界面文案已接入多语言结构。
